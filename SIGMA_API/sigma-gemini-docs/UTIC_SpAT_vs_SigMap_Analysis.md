# 도로교통공단(KoROAD) SpAT API와 UTIC 오픈API(SigMap) 데이터 규격 비교 및 보행등 렌더링 한계점 분석

## 개요
우리 앱(SIGMA)은 실시간 신호 정보를 렌더링하기 위해 UTIC 개방형 오픈 API (`getSigMapCRInfo`) 및 정적 기반정보(`L02_crossDetailInfo.json`)를 사용합니다. 반면, 도로교통공단(tsihub) 자체 웹사이트는 내부망을 통한 실시간 SpAT(Signal Phase and Timing) 데이터를 사용합니다. 이 문서에서는 두 방식의 데이터 구조 차이와, 이로 인해 발생하는 우리 앱의 **'보행등 유무 추론의 기술적 한계점'**을 기록합니다.

## 1. 도로교통공단(KoROAD) 자체 사이트의 보행등 렌더링 방식
도로교통공단의 웹사이트(`cvibInfoDetail.do`) 내 `cvib.js` 분석 결과, 보행등 표출 방식은 다음과 같습니다.
- **데이터 소스**: 실시간으로 각 방향별 상태 코드를 문자열 배열(예: `this.lightStsArr = ['3_3_1_1', '3_3_1_9', ...]`)로 수신합니다.
- **파싱 방식**: 상태 문자열의 5번째 글자(보행등 상태)를 추출(`substring(4, 5)`)하여 판단합니다.
- **렌더링 조건**: 추출된 값이 **`'9'` (데이터 없음/해당 없음)** 가 **아닌 경우**에만, 맵핑된 차량등과 동일한 각도에 보행등을 일괄적으로 렌더링합니다.
- **특징**: 이 방식은 기반정보(L02) 누락 여부와 무관하게, 실시간 데이터에서 `'9'`라는 명확한 '제외 플래그'를 제공받으므로 물리적으로 존재하지 않는 보행등(예: 대화초교의 일부 방향)을 화면에서 쉽게 숨길 수 있습니다.

## 2. 우리 앱 (UTIC 개방형 오픈API) 기반의 한계점
우리 앱은 인천(L02) 지역 실시간 통신을 지원하는 오픈 SpAT API가 없기 때문에, `SigMapCrossRoadInfoService/getSigMapCRInfo` XML API 데이터를 기반으로 TOD 스케줄을 결합하여 렌더링합니다.

- **데이터 소스**: UTIC `getSigMapCRInfo`는 현시별(Step)로 차량과 보행 신호의 On/Off 상태를 비트 값으로 응답합니다.
  ```xml
  <STEP_NO>1</STEP_NO>
  <CAR1>16</CAR1>
  <PED1>0</PED1>
  ```
- **한계점**: 이 개방형 규격에서는 보행등이 **적색(빨간불)일 때**와, **물리적으로 보행등이 아예 설치되지 않은 경우**를 구분하지 않고 무조건 `<PEDx>0</PEDx>` 으로 동일하게 내려줍니다.
- **결론**: 실시간 상태값에 `'9'`라는 식별자가 애초에 존재하지 않으므로, XML 데이터만으로는 보행등의 유무를 추론할 수 없습니다.

## 3. 해결 방안
우리 앱에서 대화초교, 주오4거리 등 기반정보에 보행등(P)이 누락되었거나 한쪽만 존재하는 특수 교차로를 완벽하게 렌더링하려면 다음 중 하나의 조건이 선행되어야 합니다.

1. **기반정보(L02 Json) 정밀화**: `L02_crossDetailInfo.js` 내 각 교차로의 현시 운영 코드(`PHASE_CONF_CD`)에, 실제로 존재하는 보행등 방향에 대한 `P...` 코드가 수동 또는 자동화 과정을 통해 정확히 매핑(추가/업데이트)되어야 합니다.
2. **SpAT 오픈API 개방 (외부 요인)**: 향후 인천시(UTIC) 등 지자체에서 서울시처럼 문자열 기반의 SpAT 실시간 연동 API를 공식적으로 민간에 개방해주어야 합니다.
